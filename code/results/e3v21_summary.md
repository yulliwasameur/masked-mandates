# E3 v2.1 -- collusion / linkage study (summary)

Generated by `sim/e3v21.py aggregate` from 565 cells (5 world seeds [20261109, 20261210, 20261311, 20261412, 20261513], identical in every setting). Full data incl. every per-seed cell: `results/e3v21.json`. Figures: `results/e3v21_main.png`, `results/e3v21_coalition.png`, `results/e3v21_sensitivity.png`.

Cells are reported as **mean [min-max over the 5 seeds]**; the bootstrap 95 % CI of the mean over seeds is in the JSON and in the sensitivity table (with 5 draws it is descriptive, not a guarantee).

## Definitions

* **Profile recovery** (was "re-identification" in v2): for a user with >= 10 calls visible to the coalition, take the attacker cluster that holds the largest number of the user's calls; the profile is recovered if that cluster holds >= 50 % of the user's visible calls AND >= 80 % of the cluster's calls belong to the user. Rate = recovered users / users with >= 10 visible calls. It measures linkage of a user's activity into one pure profile, not naming (naming = identified-tool attacker).
* **Attackers** (all tools of the coalition pool their logs): a_id identifier equality; b_timeD naive single-linkage of calls <= D ms apart unioned with identifiers; b_trackT / b_trackA ms multi-session tracker (timing [+ counter j], / + exact-amount matches) unioned with identifiers; s_atoms = stage-1 atoms (tracker-A sessions + identifier groups merged by co-occurrence); c_sessQI / d_full = 30-day hard-EM clustering of the atoms on quasi-identifiers + hour (c) and + tool set (d, combined attacker); e_oracle = **profile-oracle attacker** (atoms assigned to the max-likelihood user under the TRUE profiles; not an upper bound); id_* = identified-tool attacker (names from identifying calls; sess / clu / cls stages, see docstring).
* **Per-call top-1**: profile-oracle posterior (v2 code) puts the highest mass on the true user, from the call alone, from its reconstructed session (tracker A), from its stage-1 atom, from its a_id group and from its d_full cluster.

## Key findings (hand-written)

1. **Token format still matters against linkage by identifiers.** A stable per-tool pseudonym lets the coalition rebuild
   user profiles: profile recovery 0.93 [0.91-0.95] at N = 1,000 and 0.80 [0.79-0.80] at N = 10,000 (attacker d),
   **identical with content minimisation** (pertool_min). Per-call tokens (mm), one-time tokens (ott) and per-day
   pseudonyms give a_id = 0 by construction; the rest of this list is about the informative attackers.
2. **ott = mm exactly.** One-time tokens (batch / blind issuance) give the tools one unlinkable value per call and the same
   visible fields as Masked Mandates; computed independently, every metric, posterior and seed coincides (max difference
   0.0). Masked Mandates gains nothing over one-time tokens against a tool coalition; its advantages lie elsewhere
   (delegation, budgets, revocation), not in unlinkability towards tools.
3. **Millisecond timing does not by itself separate overlapping sessions.** The E4 v2 gaps (mm+mm_esc, median 0.81 s,
   p90 3.4 s, p99 5.6 s) are dominated by LLM latency and are broad, so the tracker reconstructs 70 % of tasks exactly at
   N = 1,000 (1-s timestamps: 68 %) but only 18 % at N = 10,000. Exact amounts add little (+1.6 points; p_quote = 0 changes
   nothing within seed noise) because only ~50 % of payments are preceded by a quote in the same task in this model.
   **Revealed counters j help a lot:** with ptej / ptejday the tracker reconstructs 88 % (N = 1,000) and 45-47 %
   (N = 10,000) of tasks exactly, with 90-93 % pair precision at N = 10,000 vs 52 % without j.
4. **Profile recovery (unsupervised, attacker d) is low for MM with content and ~0 with minimisation.** mm: 0.065
   [0.038-0.096] at N = 1,000 and 0.000 at N = 10,000; mm_min: 0.003 / 0.000. ptej (revealed j) is clearly worse for the
   user than mm: 0.22 [0.12-0.36] / 0.05. pertool_day: 0.12 / 0.00. These d values are **lower than in v2** (mm 0.23 at
   N = 1,000): v2's single seed per cell happened to give booking tools the most traffic (64 % of calls carry an origin
   city vs 4 % in seed 0 here), the mm-mode gaps are ~2x longer than the v1 E4 gaps, and tracker errors feed impure atoms
   into the clustering. Even with the TRUE task segmentation as atoms, d reaches only 0.09 on seed 0. So the drop is not
   evidence that MM got safer; it shows how strongly the number depends on which tools are popular.
5. **The profile-oracle attacker is far stronger than d**: mm 0.41 [0.22-0.67] at N = 1,000 (0.005 at N = 10,000),
   ptej 0.82, pertool_day 0.47. It is not an upper bound: it is below d for pertool / pertool_min at both N and for
   mm_min / ott_min at N = 10,000 (flagged in the F1 tables).
6. **The identified-tool attacker is the strongest result against MM, and it is bad news for MM.** When the first payment /
   booking call of a task reveals the user's name (88 % of users are named at least once in 30 days), the coalition
   attributes to the right name **68 % [54-79 %] of all MM calls at N = 1,000** (sessions alone: 54 % at 91 % precision;
   66 % of tasks) and 41 % [30-51 %] at N = 10,000. **Minimisation helps little** (mm_min 55 % / 35 %), because the
   session channel needs no content. If every task touches an identifying tool, 89 % (N = 1,000) and 56 % (N = 10,000)
   of MM calls are named correctly. MM is roughly on par with per-tool-per-day pseudonyms here (69 % / 32 %) and only
   modestly better than ptej (79 % / 65 %); it is better than stable per-tool pseudonyms (85 % / 76 %).
7. **Per-call top-1 identification (profile-oracle posterior, N = 1,000):** from the call alone 0.26 for every format
   with content (0.01 with minimisation); from its reconstructed session 0.67 (mm, pertool_day) and 0.72 (ptej); with
   minimisation 0.08-0.09. At N = 10,000: 0.13 alone, 0.37 (mm) / 0.48 (ptej) from the session.
8. **Partial coalitions.** Because popularity is Zipf, the top-5 tools already see 81 % of calls; results degrade
   slowly with k: mm profile recovery 0.037 (k = 5) -> 0.065 (k = 50); identified-tool (natural) 50 % -> 68 % of MM calls;
   every-task mode 83 % -> 89 %. A coalition of a handful of popular tools gets most of the full-coalition power.
9. **Timing mitigation (random per-call delay U(0, J), sequential loop).** Latency cost = J/2 per call after the first:
   +1.5 s / +15 s / +90 s / +900 s per task (mean) for J = 1 / 10 / 60 / 600 s. Against attacker d, **J = 10 s already
   suffices** (mm d PR 0.001, tracker exact 30 %), J = 60 s leaves the tracker at 7 %. **No J suffices against the
   identified-tool attacker:** at J = 60 s it still names 37 % (natural) / 53 % (every task) of MM calls correctly, at
   J = 600 s 34 % / 52 % -- the name then propagates through content (and through the identifying call itself), not
   through timing.
10. **Other sensitivities (N = 1,000, 5 seeds):** fewer favourites (1-3) raise mm profile recovery to 0.22 but lower
    identified-tool naming to 43 %; flatter popularity (s = 0.5) raises it to 0.14; more tasks per day (2-6) lowers it to
    0.04 (more overlap) while ptej rises to 0.43; 10x slower loops make mm unlinkable for d (0.000) but still leave 45 %
    of calls named; 10x faster loops raise d to 0.14 and naming to 76 %; gaps without proof generation ('none' mode)
    raise d to 0.10.

## Limitations

- Synthetic population and quasi-identifier model (unchanged from v2); the tool-type of the most popular tools dominates
  the between-seed variance (min-max ranges are wide, e.g. mm oracle 0.22-0.67). Five seeds; the bootstrap CI over five
  draws is descriptive. The same five seeds are used in every setting, so between-setting differences are paired.
- The tracker is greedy (no look-ahead / multi-hypothesis tracking); timing, hazard, start-rate and counter-increment
  distributions are given to the attacker from the ground truth of the same world (favourable to the attacker). A
  stronger tracker could only raise every attacker number. Identifier-group merging uses a 30 % co-occurrence ratio
  chosen on a pilot (seed 0, pertool only; no effect on other formats).
- The ptejday cross-session chaining uses a linear assignment per (day, counter level); a constraint solver would do better.
- Amount linkage: only the latest earlier booking/search call of the same task quotes the payment, and only ~50 % of
  payments have one; deployments where every payment follows a quote would strengthen the amount channel (the p_quote = 0
  sensitivity bounds the current channel's effect as small).
- Identified-tool attacker: the identifying call reveals the true user exactly; in the content stage every unnamed atom is
  forced to some named user (users never named are always counted wrong). The id_cls_conf rows give the precision of
  confident assignments.
- E4 v2 has no per-call turn index: calls are packed into tool turns (identical consecutive calls first); rows with fewer
  recorded calls than tool turns are skipped (3 + 31 of 3,840 mm/mm_esc rows). The tool timestamp is the send time; a
  constant one-way delay cancels in the gaps. Injected latency (log-normal, median 120 ms) stands in for WAN RTT.
- Payment calls are placed last in their task (search/booking first), a change from v2 that makes quotes possible.
- Partial coalitions were run at N = 1,000 only, for pertool, pertool_day, mm, mm_min, ptej (ptejday chaining assumes the
  full coalition).
